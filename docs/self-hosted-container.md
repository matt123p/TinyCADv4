# Self-hosted TinyCAD container design

## Goal

Run TinyCAD in a browser with a persistent server filesystem, native Linux ngspice with XSPICE, and server-side component library search. Publish one Linux image that people can install with Docker Compose or use as the basis for a Coder workspace. Compose serves a single workspace. Coder can provision a separate workspace and volume for each user or project.

## Application and workspace storage

Serve the existing browser editor and a same-origin API from a Node.js process. Start from the `build:fs` browser target and add a self-hosted storage adapter to the [existing `UserManager` interface](../src/io/files.tsx). The existing browser file pickers operate on the client device. In the self-hosted target, the file tree, open and save dialogs, and Project Mode should use server-backed paths. Translate the [Project Mode storage contract](../src/io/projectStorage.ts) into HTTP operations and adapt desktop-only interactions to browser upload, download, and print flows.

Mount the workspace at `/workspace` and run TinyCAD as an unprivileged user with access to that mount. Store projects, `.dsn` and `.dzn` drawings, `.tcproject` settings, personal `.tclib` libraries, and workspace preferences there. Keep bundled assets in the versioned image. In the browser, users can create or import a project, browse it, open and save its files, and download copies. A project saved from one browser should be available from another browser connected to the same workspace.

Use workspace-relative identifiers and enforce the workspace boundary on the server, including symlinks and paths supplied by Git or uploads. Preserve Project Mode's version checks for concurrent edits and use atomic writes for changes. Use one named volume per workspace and keep a documented backup and restore path. For a shared server, isolate each workspace and require authenticated access to its app. Keep a standalone Compose install bound to localhost by default and document authenticated HTTPS for access from other machines. [Docker Compose volumes](https://docs.docker.com/reference/compose-file/volumes/)

## Native Linux simulation

Use the project's qualified native ngspice bundles for Linux x64 and arm64. Each bundle includes the helper executable, shared library, manifest, and compiled XSPICE code models. The [engine build configuration](../build-support/ngspice/engine.lock.json) enables XSPICE for the native build. The current browser WebAssembly engine has XSPICE disabled. Use the [existing CI engine workflow](../.github/workflows/ngspice.yml) to source the bundles, and verify the binaries and their dynamic dependencies on the image's Linux base. [ngspice XSPICE documentation](https://ngspice.sourceforge.io/xspice.html)

Extract the reusable runtime verification, input validation, and child process handling from the [Electron launcher](../electron/simulation.js). Keep the [existing `EngineRequest` and `EngineEvent` shapes](../src/simulation/contracts.ts). The browser submits a job, streams engine-ready information, logs, vector names, waveform rows, and completion over HTTP, and can explicitly cancel a run. Use the reported capabilities to enable XSPICE features. Preserve the current chart UI and drawing result format. Keep WebAssembly available for the independent static browser build.

Run each job in a separate native helper process with a private temporary directory, a minimal environment, no network access, and access only to its staged input and trusted engine resources. Apply wall-clock, concurrency, CPU, memory, input size, and result size limits, and clean up files and processes when a job completes or is canceled. Tie jobs and output streams to their owning workspace. Apply backpressure while streaming and release abandoned jobs. Accept validated model text attachments and the image's bundled XSPICE modules. Keep control scripts, arbitrary filesystem includes, and user-supplied compiled modules outside the public simulation interface. See the [SPICE engine reference](spice-engine.md) for the desktop protocol and current validation.

## Component libraries

Package the existing bundled `.tclib` databases as read-only resources. Build a catalog index from their names, descriptions, and attributes, and query it in Node with native SQLite. Reuse the [native `.tclib` reader](../shared/tclibSqlite.mjs) and the desktop tests as a reference for symbol data, including attribute ordering and SPICE metadata. Run synchronous SQLite work off the Node request thread.

Expose catalog listing, paginated symbol search, and individual symbol details. Send only result metadata for lists and fetch full artwork, attributes, and SPICE identity on preview or placement. Use the same search backend for the library panel and assistant search. Keep placed symbols embedded in the drawing so downloaded schematics remain portable. Store personal libraries in `/workspace` and keep them out of other workspaces' search results. Personal library editing can continue to use the existing file format and save workflow. [Drawing format](drawing-format.md) · [Library reference](libraries.md)

Moving an entire decoded library to the browser still leaves all of its names and artwork in the tab. The query API is the change that reduces client heap and transfer sizes. Measure both with a large library and an all-library search before setting a memory target. The initial Electron native reader still returns a decoded library through IPC because the desktop library UI expects that shape. A later Electron change could reuse the paginated model over IPC.

## Build and publish

1. Build an image with the browser assets, Node runtime, native engine for the target architecture, and bundled catalog. Use a multi-stage build and a health check for the HTTP service. Verify the packaged binaries and assets in CI before publishing. [Docker multi-platform builds](https://docs.docker.com/build/building/multi-platform/)
2. Publish one public multi-architecture image for `linux/amd64` and `linux/arm64` on GitHub Container Registry. A possible image name is `ghcr.io/matt123p/tinycad-web`. Publish versioned tags from the release workflow and link each release to its matching source, build and packaging files, and license and third-party notices. Public package visibility allows anonymous pulls. [GitHub Actions publishing guide](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images) · [GitHub Container Registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) · [TinyCAD license](../license.md)
3. Attach a ready-to-use `compose.yaml` to each GitHub Release and link it from the installation section. Pin it to the release's image version, map `127.0.0.1:8080` to the application port, and mount a named volume at `/workspace`. The install flow is to download the file, run `docker compose up -d`, and open `http://localhost:8080`. Document updates with `docker compose pull` followed by `docker compose up -d`, and include backup and restore instructions for the volume. [Docker Compose startup](https://docs.docker.com/reference/cli/docker/compose/up/)
4. Offer a Coder Terraform template for teams using the Coder platform. Use the same application image as Compose, add the Coder agent as needed, and provision a durable volume for each workspace. Expose the HTTP service as an owner-only `coder_app` so a user can click **TinyCAD** after creating a workspace. Include the template in the repository and publish an importable archive. Test stop, restart, update, and the documented deletion behavior. [Coder Docker template](https://registry.coder.com/templates/coder/docker) · [Coder template import](https://coder.com/docs/admin/templates/creating-templates)

## Implementation and acceptance

1. Deliver the browser target and persistent volume first. Create or upload a project, edit and save it, recreate the container with the same volume, then reopen the project from another browser. Exercise workspace-boundary and concurrent-save behavior.
2. Run a qualifying analog and XSPICE mixed-signal example through the browser on both image architectures. Compare the results with the existing native qualification tests and verify cancellation, timeout, and cleanup.
3. Add server catalog search and on-demand symbol details. Open and preview a large library, place a symbol, save the drawing, then reopen the downloaded file in desktop TinyCAD. Compare browser memory and network transfer with the current full-library flow.
4. Verify a clean Compose install can pull the public image, create a workspace, and retain data through an upgrade. Verify that two Coder workspaces get separate storage and can only access their own app.

If immediate Electron feature parity is needed for a prototype, the Linux desktop build can run in a virtual display and stream over noVNC. That gives browser access to the existing desktop UI and native engine. The design above gives the browser editor direct workspace file transfers and a query-based catalog. [noVNC project](https://github.com/novnc/noVNC)
