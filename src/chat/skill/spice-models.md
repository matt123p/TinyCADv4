## SPICE models when requested

Work on SPICE only when the user explicitly requests SPICE or simulation support. For ordinary symbol or schematic work, preserve any model supplied by the library and skip model research, generation and attachment. A request to find or explain a model is read-only. Attach or replace a definition when the user asks for that change. Get approval before replacing an existing custom definition.

1. Start with `search_spice_models` in either editor mode. Try the exact chip, aliases, a documented drop-in replacement, then a generic model for the device family. The bundled catalog is available without a datasheet or web access. Use `inspect_spice_model` with the exact `modelId`, `packId` and `revision` to read the model and its dependencies. Cite the returned source. Call a substitution an approximation and explain which behaviour or ratings it leaves unverified.
2. Verify the physical symbol pin numbers independently from the model's terminal order. A model can describe a single amplifier channel or omit a chip's trim and NC pins. A missing datasheet does not prevent model research, but the model's port names alone cannot establish the package pinout. A drop-in chip still needs verified pin functions, supply polarity and operating conditions before its model can be used. Ask about any mapping that cannot be resolved.
3. Use `inspect_spice_target` with the exact model identity and either a placed reference and sheet or a retained `componentId`. Supply that same target to `search_spice_models` to check available choices. Tagged SPICE essentials symbols use preverified mappings and already have a bundled default. For other symbols, review suggested pins and pass distinct physical pin numbers in model-terminal order.
4. In a drawing, place a new symbol with `place_component`, inspect its placed reference, then call `attach_spice_model` with that reference, sheet and the inspection's current revision as `baseRevision`. In a library, pass `spiceModel` on the relevant item in `add_library_components` so future placements inherit the linked model. Supply the exact model identity and reviewed mapping. Use `replaceExisting` only with the user's approval for a custom definition.

### Custom definitions

Use a self-contained Custom definition if the user asks for a new model or model edits and a bundled link does not meet the simulation requirements. For new symbols, pass `customSpice` to `place_component` or on the item in `add_library_components`. The object takes `template` (required) and optional `prologue` and `epilogue`. For a placed symbol already using a bundled model, TinyCAD's **SPICE → Custom** switch creates an editable local copy. For an existing reusable library entry, edit it under **SPICE → Custom** and save the library to set its future placement default.

The symbol artwork and model are separate. TinyCAD stores the Custom instance statement in hidden `$$SPICE`, definitions in `$$SPICE_PROLOG` and optional trailing text in `$$SPICE_EPILOG`. For example, `DTC_$(ref) %(1) %(2) LOCAL_DIODE` uses the placed reference and the nets wired to physical pins 1 and 2. Its prologue can declare `.model LOCAL_DIODE D(IS=1n)`. For a subcircuit use an X instance and order the pin macros by the `.subckt` declaration. Include required model cards and helper subcircuits. Use names unique to the model or instance when definitions differ. Put analyses and run settings on the Simulation sheet and use net `0` as SPICE ground.

Reinspect the placed symbol or read back the library entry to confirm the saved link or Custom fields. Check the expanded pin order against the circuit. State which checks you actually ran and whether simulator behaviour was tested.
